# The New World — Connected Encyclopedia v2

This release adds a **shared, additive knowledge layer** to the existing local-first World Bible Studio. The Reader and Studio continue to use one canonical entity store, existing UUIDs, existing Markdown, and existing publication decisions.

## What works

- Built-in type-aware properties and subtype choices for place, person, organization, family, event, subject, object and source. Unknown fields are rejected; entry-valued fields must point to the same world.
- World-specific hierarchical collections (categories) and reusable flat topic tags. An entry can have multiple collections and tags. The Library and Reader both have collection/tag filters.
- Markdown-aware title/alias discovery in the Studio: **Discover references** identifies candidates, reveals ambiguous matches, and supports author approval or ignore. Approval writes permanent UUID-backed wiki links; ignored matches persist for unchanged paragraph context.
- Explicit existing typed relationships, links, media, status, publication and history remain intact.
- Reader sees published-only collections, tags, membership and type-aware fields; unpublished entry references within public structured properties are omitted.
- Static exports include the public-safe v2 classification data.
- v2 JSON exports include categories, tags, structured entry metadata and assignments. v1 JSON imports remain supported.

## Data and migration

At startup, `Store` upgrades database `PRAGMA user_version` to 2. Before upgrading an existing v1 database, the server creates a complete archive at `.worldbible/backups/before-knowledge-v2.zip` using SQLite's online backup API, including any media originals.

All old entity IDs, article bodies, relationship and publication rows remain unchanged. v2 adds only separate `entry_details`, `categories`, `tags`, `entity_categories`, `entity_tags` and `mention_decisions` tables. Upgrading is idempotent. Keep the backup until the new Reader and Studio have been checked locally.

JSON export is **metadata-only** and does not carry image binaries. Use the full backup utility to preserve media. Imports always create a new isolated world and remap UUID references.

## Using Studio

1. Select **Encyclopedia** in the Library group.
2. Select an entry and open **Write**.
3. Under **Entry properties & classification**, choose a subtype (if appropriate), fill structured properties, assign collections or tags, and select **Save properties & classification**.
4. Save article prose separately using **Save entry**.
5. Select **Discover references** after saving article edits to review existing-title and alias matches. Accept an explicit target to insert a permanent link, or ignore that match.
6. Use the left explorer's Collection / Topic filters to find classified records. **+** beside the new collection box creates a collection, nested under the currently selected collection.

## Using Reader

The Reader starts at `/read/`. It displays only published articles. On the homepage, published collections provide navigation beyond entry types. In **Encyclopedia**, filters for type, collection and topic can be combined with text search. Article pages show public collection/tag links and relevant structured fields.

The offline static site produced by `app/publish_site.py` uses the same classification data without an authoring API.

## API summary

Studio GET: `/api/v2/types`, `/api/v2/categories`, `/api/v2/tags`, `/api/v2/memberships`, `/api/v2/metadata`, `/api/v2/mentions`, `/api/v2/search`.

Studio POST: `/api/v2/categories`, `/api/v2/tags`, `/api/v2/metadata`, `/api/v2/mentions/approve`, `/api/v2/mentions/ignore`. All write requests retain the local write header and origin checks.

Reader GET: `/api/v2/public/categories`, `/api/v2/public/tags`, `/api/v2/public/memberships`, `/api/v2/public/metadata`, `/api/v2/public/search`.

All world-specific URLs require `world_id`. Entry-specific URLs also use `id`. Explicit mentions have a body SHA-256 revision and positional fingerprint to prevent applying stale suggestions.

## Scope limits

This implementation deliberately keeps the existing local Python/SQLite/vanilla-JavaScript stack rather than introducing a new framework or graph database. Search uses SQLite text matching. Complex custom property-schema editing, AI-generated relationship assertions, historical date-basis conversions, and advanced performance indexing are not included; they require separate validation before making stronger claims about chronology or scaling. The app currently presents existing year values without fabricating calendar conversions.

## Verification

Run `python -m unittest discover -s app/tests -v` and the existing GitHub Actions Studio/Reader browser smoke tests. Windows CI covers backup/restore and legacy cleanup behavior. Do not manually alter or delete the `.worldbible` database during migration.
